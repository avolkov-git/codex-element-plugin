# React Chat Webview

The existing `WebviewPanel` mounts a locally bundled React/TypeScript application.
`media/chat.js` is generated by `scripts/build-chat-ui.js`; do not hand-edit it.
There is no dev server, CDN, SSR, runtime import, or eval requirement. The entry
sets the existing ready guard before initializing modules so a late external
script cannot acquire the VS Code API twice after the nonce inline fallback.

## Build And Check

- `node scripts/build-chat-ui.js --check`: compile in memory and validate notices;
  does not write media or dist.
- `npx tsc -p webview/chat/tsconfig.json`: type-check without emitting files.
- `node scripts/chat-ui-check.cjs`: native Chrome through the bundled Playwright
  runtime, no dev server; screenshots go to a temporary output directory.
- `node scripts/chat-questions-check.cjs`: inline native and async questions,
  answer routing, errors, secret handling and drafts across virtual scrolling.
- `node scripts/build-chat-ui.js`: emit only `media/chat.js` and
  `media/chat.NOTICES.txt`. React, Markdown, icons and virtualization packages are
  development dependencies used at build time, not extension-host requirements.

Full bundled dependency licenses are generated deterministically from esbuild's
actual input metafile by `scripts/third-party-notices.js` and ship with the media.
The highlighter remains an independently generated local preload, including in
the HTTP inline fallback provided by `src/webviewHtml.ts`.

## Data Contract

`ChatPanelManager` exports the typed `ChatBridgeFrame`/`ChatBridgeMeta` contract.
It coalesces notifications for 48 ms, sends one initial snapshot, then changed
entities and append-only text patches. Only one frame may be unacknowledged.
ACK names the chat, epoch, and revision. It means the entity store accepted the
frame, not that React painted it or that history was durably saved. Missing
revisions request resync; ACK timeout and visibility resume start fresh epochs.
Identical snapshots are suppressed. Hidden panels retain only a dirty flag.

The client retains sparse reading/tail windows (normally at most 600 entities,
trimmed to 480), current parent metadata, and selected rows. TanStack Virtual
measures variable row heights in the iframe. User navigation disables following
without freezing live entities. Selected rows retain their data/DOM until the
selection is released. The composer is independent of transcript DOM updates;
drafts and completed attachment references are restored via webview state.

Completed activity/worklog/compaction rows group under their parent turn even
when it is outside the fetched window. Running operations and all diff/message
rows remain inline. Turn children load in 40-item pages; large child collections
load in 20-item pages. Bridge frames contain summaries, not tool output/diff
bodies. Detail previews have explicit size limits; native file diff opens the
complete artifact. Expandable details refresh on status/update changes.

## Host Commands

Every command carries its originating `chatId`, including asynchronous upload,
question, approval, and feature requests. Commands are not redirected to whichever
chat becomes active while a request is being handled.

- `chat.viewport {offset}`, `chat.ack`, `chat.resync`, `chat.visibility`
- `chat.turn.load {turnId,offset,requestId}` -> `chat.turn.window`
- `chat.item.load {id,offset,requestId}` -> `chat.item.detail`
- `chat.userInput.respond {id,response}` -> `chat.userInput.result`, where
  response is exactly `{answers:{questionId:{answers:["answer"]}}}` or `null`
  to cancel. Native answers are never written to webview draft state.
- `chat.question.respond {messageId,questionId,answer}` -> `chat.question.result`
  for persisted async questions and planning clarifications. The host validates
  ownership and sends the answer to the originating chat, never the active chat
  inferred later. Success is reported only after the runtime accepts the input.
- `clipboard.write {text,requestId?}` -> `clipboard.result`, using the host API
  even on insecure HTTP where browser clipboard access is unavailable.
- Existing send, queue, steer, stop, attachment upload/pick/paste, plan, model,
  effort, speed, skill, rules, approval, restore and IDE-link commands remain.

Optional feature requests use `{type:"features.request",requestId,command,payload,
chatId}` and receive `{type:"features.result",requestId,result,error,chatId}`.
Search/import, review/comment/stage/revert, capability-checked project actions,
browser artifacts, and chat fork use this route. Missing handlers produce an
explicit unavailable state. Mutation controls require capability/revision data
and confirmation; the feature service remains responsible for concurrency checks.

`ensureHistoryLoaded` is optional and awaited for restored panels, open, and ready.
Its implementation, native input resolution, queue retry, and feature services
are supplied by the extension/runtime owners. No identity selection is inferred
from arbitrary profile names in this UI.

## Verification Boundary

The frontend fixture uses the real `ChatPanelManager` and browser bundle with
in-memory host data. It covers 1,000/10,000 variable-height histories, streaming
while reading/selecting, draft restoration, epoch/ACK/visibility backpressure,
origin-chat routing, approval dialog focus/inertness, inline question/secret handling, paginated
operations, clipboard, upload/paste, and feature controls. It is not a claim of
Windows/Element server end-to-end acceptance or authorization to deploy.

## Вопросы в истории

`agentMessage.questions` используется только для структурированных асинхронных
вопросов app-server. Кнопка варианта отправляет ответ сразу; свободный текст
отправляется кнопкой «Ответить» или Enter. Служебные вопросы планирования
используют те же элементы управления. Произвольный текст Markdown не разбирается
эвристически, даже если в нём есть вопросительный знак и список.

Черновики асинхронных ответов живут в памяти текущего чата отдельно от виртуальных
строк. Прокрутка и новые токены не удаляют их; результат отправки обрабатывается
и когда строка за пределами окна. Они не записываются в `vscode.setState`.

Активные RPC-формы `item/tool/requestUserInput` расположены после виртуальной
истории внутри того же скроллера. Они не размонтируются при прокрутке и не
перехватывают фокус при появлении. Несколько вопросов одного RPC отправляются
вместе после заполнения; отдельные запросы независимы. При закрытии запроса его
секретные ответы удаляются вместе с формой. Модальные подтверждения разрешений
не относятся к этим вопросам и сохраняют прежнее поведение.
