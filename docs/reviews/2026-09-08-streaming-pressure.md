# Обрывы IDE при длительной работе Codex

## Цель и границы проверки

Устранить подтвержденные источники перегрузки плагина и получить измерения,
по которым можно отличить задержку интерфейса от обрыва транспорта Theia,
перезапуска plugin-host и нехватки памяти на сервере.

Переданный разбор относится к 0.1.88. Работа выполнена в ветке
`codex/1.0.0-rc`, поверх `d337e98`, для сборки `1.0.1-rc`.
`master`, стабильная 0.1.89 и предыдущая поставка RC не изменяются.

Свежих логов проблемного сервера нет. Причина конкретного обрыва
**не доказана**. Локальные тесты не воспроизводят весь WebSocket-транспорт
Theia и не подтверждают исправление серверного heartbeat timeout.
Увеличение Java `worker-thread-count` не является исправлением очередей Node.

## Что осталось после первого RC

Первый RC уже использует React, оконный список, пакетные обновления,
дельты текста, подтверждения сообщений и остановку обновлений скрытого чата.
JSON-RPC уже ограничен 8 MiB; основной снимок чата уже не содержит полный diff.
Эти пункты старого разбора нельзя считать неисправленными в новом RC.

Подтвердились другие проблемы:

- Таймаут ACK сбрасывал мост, даже если старый `postMessage` еще ожидал
  завершения. Это допускало повторные отправки при медленном транспорте.
- Sidebar отправлял полный снимок на каждой дельте, включая неиспользуемые
  им очереди сообщений и данные подтверждений.
- Полный diff оставался в StateStore и истории; парсер делал `split` всего
  текста и собирал патчи построчным наращиванием строк.
- Каждое streaming-уведомление отдельно логировалось. Очередь записи не была
  ограничена, OutputChannel обновлялся на каждую строку.
- Последовательные завершения операций создавали отдельные полные сохранения
  истории с повторной сериализацией и сравнением одних данных.
- Загрузка и поиск по корпусу документации выполнялись в plugin-host.

## Исправления 1.0.1-rc

**Чат.** Незавершенный `postMessage` учитывается отдельно от ACK. Таймаут не
разрешает новую отправку. Позднее подтверждение возобновляет поток одной
накопленной дельтой. Явный resync/возврат видимости начинает новый снимок;
скрытая панель не обновляется. После ошибки доставки ожидание продолжается
до сигнала готовности клиента, без бесконечного цикла повторов.

**Список диалогов.** Пакетирование 100 ms, один неподтвержденный снимок,
подавление одинаковых данных и скрытых обновлений. Передаются только поля,
которые список показывает. Изменение `updatedAt` не перерисовывает работающий
чат, пока вместо времени показан индикатор выполнения.

**Diff.** Полный текст хранится отдельно, в `<область пользователя/проекта>/patches`.
История содержит непрозрачную ссылку, диапазон и превью до 2048 символов на файл,
с общим бюджетом превью 128 Ki символов на обновление. Полная запись читается
только при открытии патча в редакторе. Она не является снимками двух полных
версий файла; текущий Git review остается отдельным механизмом.

Одна запись ограничена 8 MiB. Очередь: до четырех ожидающих записей и 16 MiB,
плюс одна активная запись до 8 MiB; обновления одного turn объединяются.
Кэш: до 128 файлов/256 MiB после очистки. При заполнении очереди, ошибке диска
или вытеснении записи сохраняется ограниченное превью с явной отметкой.
Native preview ограничен 1,9 млн символов. Метаданные ограничены 1024 файлами
плюс явной строкой оставшихся изменений, счетчики добавлений/удалений сохраняются.
Доступ проверяет область пользователя, хеш, диапазон и отсутствие выхода через symlink.
Файлы проекта не изменяются; права новых файлов 0600, каталога 0700 на Unix.

**Логи.** Нет записи каждой streaming notification. OutputChannel и файлы
обновляются пакетами: до 512 записей/256 KiB в очереди и один пакет до
128 записей/64 KiB в работе. При перегрузке информация отбрасывается первой,
но даже ошибки не имеют бесконечной очереди. Потери, ошибки записи и
отбрасывание слишком длинных строк учитываются в счетчиках. `flush` и экспорт
имеют границу принятых записей и не ждут бесконечно нового трафика.

**История.** Один активный и один заменяемый пакет сохранения в обычном случае;
жесткий предел 32 операции. `flush`, загрузка, импорт и отправка сообщения из
очереди сохраняют порядок и подтверждение записи. Пакеты не объединяются между
пользователями, проектами или workspace. Сравнения используют хеши чатов;
неизменившиеся данные не записываются повторно. Перед сохранением диск все равно
читается под блокировкой: кэш не скрывает сторонние изменения или повреждение.
Резервная копия сохраняет исходные байты проверенного файла.

**Документация.** Отдельный лениво запускаемый worker, один активный запрос,
до восьми ожидающих, deadline 30 s, ограниченные ответы до 1 MiB. Кэш до четырех
корней, 60 тыс. фрагментов и 64 млн символов; чтение JSONL потоковое.
Ограничение old generation worker 384 MiB не равно лимиту RSS всего процесса.
Есть отмена при изменении настроек, проверка fingerprint, восстановление после
сбоя и остановка через минуту простоя. Сканирования корпуса на activation нет.

## Метрики

Каждые 10 секунд в `plugin.log` и Output: Codex появляется строка
`Pressure metrics: {...}`. Только числовые/логические счетчики из фиксированного
списка: без текстов чатов, содержимого файлов, запросов поиска и учетных данных.
Новые очереди, поток RPC и метрики остаются ограниченными и при ошибках.

| Поле | Значение |
| --- | --- |
| `process.pid`, `ppid`, `ownedCodexPid` | Корреляция с процессами сервера |
| `process.rssBytes`, `heapUsedBytes` | Память plugin-host, не всей IDE |
| `eventLoop.maxMs`, `p95Ms` | Задержка plugin-host за интервал |
| `sources.runtime` | Число/байты RPC-строк, пик размера и времени обработки |
| `sources.chat.frames`, `bytes`, `maxFrameBytes` | Накопленные отправки и размер; частота считается разностью за интервал |
| `pendingPosts`, `pendingAck`, `ackAgeMs`, `ackTimeouts` | Очередь доставки и ожидание клиента |
| `frontendLagMs`, `frontendReceiveMs` | Максимумы webview из полученных ACK; не внешней оболочки Theia |
| `sources.chat.sidebar` | Отправки списка диалогов |
| `sources.history` | Сохранения, очередь, время и объем сериализации |
| `sources.history.store.persistedBytes` | Размер последнего подтвержденного `chats.json` |
| `sources.diff` | Размер патчей, очередь, объединение, потери и вытеснение |
| `sources.docs` | Worker, очереди, cache, timeout и отдельная стоимость metadata |
| `sources.logger` | Очередь, пакеты, потери и ошибки доставки логов |

RSS Java, Theia backend и Codex app-server автоматически не измеряется.
Их нужно сопоставить по PID и времени средствами сервера/контейнера.
Сборщик не запускает `sudo`, не сканирует чужие процессы и не меняет системные
настройки. Зависание plugin-host задержит и его метрики; пропуск строки сам
по себе не доказывает OOM.

## Локальное воспроизведение нагрузки

- 10 000 сообщений, 1200 дельт, 24 diff по 1 162 960 байт, задержка моста 90 ms:
  51 отправка, 235 908 байт суммарно; крупнейшая 44 368 байт.
- Максимум один `postMessage` в работе, 21 строка в DOM, смещение позиции
  чтения 0 px. Выделение и черновик сохранились, финальная дельта доступна.
- Пиковая задержка event loop тестового host 24,5 ms; parse diff до 15,1 ms.
  Измерения относятся к локальному Mac и синтетическому мосту, не к серверу.
- На Node 22.13.1, как в исследованном бандле, 26 000 фрагментов:
  во время холодного/теплого поиска 133 срабатывания host-таймера,
  максимальный промежуток 6,5 ms. Результаты совпали с прежними search helpers.
- 120 изменений, 24 чата/960 элементов: две записи истории вместо отдельной
  записи на каждое изменение. Проверены сохранение перед dispatch, конкуренция,
  повреждение диска, raw backup и смена пользователя.

Команды из корня репозитория:

```sh
npm run check:pressure
npm run check:chat-pressure
npm run check:identity
npm run check:chat-ui
```

Stress-проверка пишет `pressure-metrics.json` и `streaming-scroll.png` во временный
каталог; путь выводится по завершении. `CODEX_TEST_ARTIFACTS` задает другой каталог.
Тесты используют временные данные, не меняют локальную документацию или приложение.

## Что проверить на сервере

1. Сохранить предыдущий плагин и config root. Установить платформенный `1.0.1-rc`,
   убедиться по настройкам, что запущена именно эта версия.
2. Зафиксировать версию Element, время/часовой пояс и PID из метрик. Проверять
   в тестовой копии проекта, с тем же корпусом документации и тем же запросом.
3. Оставить 1-2 минуты простоя для базовых метрик. Затем повторить длительный
   запрос, прокручивая историю во время ответа; отдельно повторить при скрытом чате.
4. При обрыве сохранить время, WebSocket close code/reason и Console браузера,
   `plugin.log`, `runtime.log`, свежие логи Theia и server.log. Не присылать
   содержимое `auth.json`, config с секретами или необработанный сетевой HAR.
5. На сервере проверить, изменились ли PID, `restartCount`, cgroup
   `memory.events`/`oom_kill`; сопоставить RSS Java/Theia/plugin-host/Codex.
   В Docker отдельно проверить `OOMKilled`, restarts и общий memory limit.

Рост `ackAgeMs` при нормальном host lag указывает на участок доставки/браузер,
но не различает их сам. Рост host lag указывает на блокировку plugin-host.
`1009` требует проверки размера кадров и лимитов прокси; `1006` не доказывает
конкретную причину. Смена PID или подтвержденный `oom_kill` отделяют рестарт/OOM
от задержанного heartbeat. Без этих данных нельзя объявлять причину установленной.

## Остаточные ограничения

- Сохранение истории не вынесено в worker: изменившаяся история и backup все еще
  читаются/записываются целиком, верхняя граница 128 MiB. Локальная запись истории
  13,37 MB заняла около 116 ms, пиковая задержка event loop 27 ms. Большие истории
  на медленном диске нужно измерить отдельно; JSONL сам по себе этого не решает.
- Метаданные документации остаются в SettingsService на host, чтобы не выдавать
  предположения за действительную конфигурацию. Их стоимость измеряется отдельно.
- Worker разгружает host event loop, но потребляет память того же plugin-host.
  Работа при жестком лимите памяти контейнера не гарантируется одним worker limit.
- Есть лимиты RPC, превью, артефактов и очередей, но нет обещания ограничить суммарную
  память Java, Theia, Chromium, Codex и всех иных расширений.
- Windows/Linux Element и конкретный service account не запускались локально.
  Нужен свежий приемочный запуск `1.0.1-rc`; ограничения `noexec`, права, SELinux/AppArmor
  и настройки reverse proxy остаются частью окружения сервера.
