# Ревью плагина и архитектуры чата

Дата: 2026-09-08. Проверяемое состояние: `0.1.89`, `master`, HEAD `c792a77` и существующие незакоммиченные изменения обновления app-server до `0.153.4`.

## Цель

Сделать чат устойчивым при прокрутке во время поступления ответа: пользователь не теряет место чтения, выделение, введенный текст и возможность взаимодействовать с сообщениями. Сохранить клиент-серверную архитектуру Theia и работающие интеграции. Переход на React рассматривается как средство сопровождения интерфейса, а не как самостоятельное исправление производительности.

Это ревью, не выполненная миграция. Рабочий код, версия, deploy и release в ходе ревью не изменялись. Предыдущие изменения сохранены.

Дополнение: [проверка реализуемости в бандле 1С:Элемента 9.2.4-6](2026-09-08-element-bundle-feasibility.md). Она уточняет рекомендации ниже: HTTP webview требует полноценного inline bootstrap, Worker требует отдельного CSP/loading contract; обычные terminal actions ограничены режимом Element, а штатные Git-команды могут выполнять push. Worktrees и trusted multi-user identity не считаются готовыми plugin-only возможностями.

## Вывод

**Переход на React + TypeScript рекомендован, постепенно, внутри существующего WebviewPanel.** Причина: ручное управление HTML, состоянием, фокусом, обработчиками и окнами истории уже дает несколько воспроизводимых ошибок. Сначала нужны исправления сохранности данных и модели обновлений; перенос существующего `root.innerHTML` в `dangerouslySetInnerHTML` этих ошибок не устранит.

Выявлено 11 приоритетных проблем: 4 уровня P1 и 7 уровня P2. P0 по проведенным проверкам не обнаружены. Условия возникновения и границы доказательств указаны ниже.

## Подтвержденные проблемы

### F01 [P1] Поток ответа пересоздает скроллер и замораживает просматриваемые сообщения

Места: `media/chat.js:258`, `media/chat.js:516`, `media/chat.js:539`, `media/chat.js:3353`.

При уходе с конца чата `syncTranscriptWindowFromSnapshot()` оставляет старые объекты сообщений. Меняются только счетчики окна. Затем `tryPatchStreamingTranscript()` не находит изменений и возвращает `false`. Это трактуется как необходимость полной замены `root.innerHTML`, включая сам прокручиваемый элемент и composer.

В браузерном тесте: 15 обновлений у конца чата дали 0 замен скроллера; после прокрутки вверх 30 обновлений дали 30 замен. Выделение длиной 81 символ стало пустым. Текст активного сообщения остался старым и после получения completed snapshot. Ошибок JavaScript при этом нет.

Следствие: чтение истории конфликтует с потоком ответа; восстановление численного `scrollTop` не сохраняет идентичность скроллера, выделение и браузерное поведение прокрутки. Замороженные данные также искажают статус завершения. Это воспроизведенный механизм, а не вывод только из размера файла.

Исправление: стабильный scroll container; отдельный успешный результат для no-op update; обновление сущностей по ID независимо от положения пользователя; изменение только затронутых узлов. Следование за концом и свежесть данных должны быть разными состояниями.

### F02 [P1] Ошибка чтения истории может привести к перезаписи исходного файла

Места: `src/chatHistoryService.ts:24`, `src/chatHistoryService.ts:37`, `src/chatHistoryService.ts:107`; вызов сохранения: `src/extension.ts:84`.

Любая ошибка, кроме отсутствия файла, заканчивается возвратом `undefined` и запуском с пустой историей. Следующее сохранение заменяет тот же `chats.json`. Нет запрета записи после неуспешной загрузки, карантина поврежденного файла или резервной копии.

Подтверждено на отдельном искусственно поврежденном файле: `load()` вернул пустое состояние; `saveNow()` заменил оригинал новым чатом; в каталоге остался только новый `chats.json`. Реальная история пользователя не затрагивалась.

Исправление: различать `missing`, `loaded`, `corrupt`, `unreadable`; не писать поверх исходника при последних двух состояниях; сохранять backup и давать явное восстановление. Atomic rename защищает от части ошибок записи, но не от этой ошибки загрузки.

### F03 [P1] Проверка browser runtime синхронно читает сотни мегабайт

Места: `src/browserRuntimeService.ts:239`, `src/browserRuntimeService.ts:50`, `src/settingsPanelManager.ts:386`.

`fs.readFileSync(candidate).subarray(0, 128)` сначала читает весь файл и только потом отбирает заголовок. Проверка вызывается через `getView()` при формировании snapshot настроек, в том числе при обновлении интеграций.

У проверенной Linux-поставки Node занимает 123656816 байт, Chromium 197004624 байт, launcher 1192 байта. Итого один проход читает 320662632 байта, около 321 МБ. Размеры измерены по реальным файлам; время чтения на пользовательском сервере не измерялось. На медленном диске это блокирует plugin host, на быстром остается лишняя аллокация и нагрузка на GC. Это отдельная проблема, не обязательное условие F01.

Исправление: читать только заголовок через ограниченный `read`, кэшировать результат по пути/mtime/size, не валидировать неизменные бинарники на каждом UI snapshot. Тяжелые проверки выполнять асинхронно по явному действию.

### F04 [P1] Новый пользователь может автоматически получить единственный чужой профиль

Место: `src/userProfileService.ts:31`.

Условия: у нового экземпляра IDE нет переменной идентичности Element и сохраненного выбора, а в общем config root существует ровно один профиль. В этом случае `getKnownProfileId()` выбирает его автоматически. Имя каталога не доказывает принадлежность профиля текущему пользователю.

Изолированный тест с пустым окружением и одним профилем другого условного пользователя подтвердил такой выбор. Реальный вход в чужую учетную запись не выполнялся. Риск актуален именно при общем хранилище и отсутствии надежной идентичности; это не утверждение, что установленный сервер уже смешивает учетные записи.

Исправление: не выводить личность пользователя из количества каталогов. При неизвестной идентичности нужен отдельный профиль или явный безопасный выбор с проверкой принадлежности. На многопользовательском сервере закрепить контракт между Element identity, профилем, workspace и правами хранения.

### F05 [P2] На каждый фрагмент ответа передается полный snapshot окна

Места: `src/chatPanelManager.ts:125`, `src/stateStore.ts:174`, `src/codexRuntimeController.ts:2253`, `src/extension.ts:267`.

Каждый assistant delta приводит к `postMessage` с полным snapshot: окно последних 120 элементов, контекст, каталог моделей и другие поля. У tool/diff/completion событий нередко вызываются и `onDidChange`, и `onDidChangeChat`; оба пути отправляют снимок активного чата. Нет объединения обновлений, ожидания обработки потребителем и пропуска одинаковой ревизии. Сам факт скрытия panel также не исключает отправку.

Синтетический снимок 61 текстового элемента занимал 35509 байт. Это не измерение трафика реальной Theia: ее транспортные расходы и задержки отдельно не измерялись. Скрытые diff и output внутри окна способны существенно увеличить payload.

Исправление: initial snapshot + небольшие versioned patches; пакетирование текстовых delta; критические завершения, ошибки и approvals доставлять без длительной задержки. Большие diff/output запрашивать отдельно. Добавить `chatId`, `revision`, `requestId`, обнаружение разрыва последовательности и resync. Не терять события при объединении.

### F06 [P2] Новые Markdown-ссылки не работают во время streaming

Места: `media/chat.js:611`, `media/chat.js:3376`.

Полный render навешивает click handlers на `[data-command]`. Streaming patch заменяет HTML сообщения, но не подключает обработчики к новым кнопкам-ссылкам.

Тест: ссылка появилась при точечном обновлении, клик не отправил команду. После полного render тот же клик отправил `markdown.openLink` с правильным путем.

Исправление: делегирование событий от стабильного узла или React handlers в компонентах ссылок. Тест должен кликать ссылку до завершения ответа; существующий тест разбора пути не проверяет это поведение.

### F07 [P2] Окно истории может отделить операции от родительского turn-run

Места: `src/stateStore.ts:268`, `media/chat.js:2573`, `media/chat.js:2614`.

Сервер отдает `transcript.slice(...)`, renderer строит связи только по текущей странице. Если `turn-run` остался за ее границей, worklog больше не считается принадлежащим свернутому завершенному turn. В обратном случае раскрытие родителя показывает лишь попавших в окно потомков.

Подтверждено fixture: один и тот же завершенный worklog видим без parent и скрыт при наличии свернутого parent. Это зависит от границы окна, а не от пользовательского выбора.

Исправление: выдавать metadata родителя независимо от страницы; строить presentation rows по turn/item ID; дочерние списки раскрывать с собственной загрузкой. Не превращать огромный turn в один безразмерный DOM-блок и не считать raw activity rows единицами пользовательской пагинации.

### F08 [P2] Stop может завершиться, хотя дочерний процесс еще жив

Места: `src/runtimeProcessManager.ts:21`, `src/runtimeProcessManager.ts:39`, `src/runtimeProcessManager.ts:70`.

После `child.kill()` значение `child.killed` означает отправку сигнала, не завершение процесса. Проверка `if (!child.killed)` в таймере пропускает SIGKILL. Процесс, который игнорирует SIGTERM, продолжает работать, но `isRunning` уже false. Поздний exit старого процесса также безусловно очищает `this.child`, что опасно при повторном запуске.

На macOS искусственный Node-процесс с обработчиком SIGTERM остался жив после `stop(100)`. В конце теста он принудительно завершен. Сценарий Windows с такой семантикой сигналов не воспроизводился. Значение `killed` подтверждено [документацией Node.js](https://nodejs.org/api/child_process.html#subprocesskilled).

Исправление: состояние lifecycle до события exit/close, stop single-flight, escalation по факту завершения, проверка идентичности дочернего процесса в callbacks. Отдельно проверить очистку созданных MCP/Chromium потомков на целевых ОС.

### F09 [P2] Подсветка растущего кода выполняется целиком на UI-потоке

Места: `webview/highlight/index.ts:96`, `webview/highlight/index.ts:119`, `media/chat.js:4157`.

Promise не переносит semantic pass и `codeToHtml` с главного потока браузера. Каждая новая версия кода имеет отдельный cache key. Лимит 160 записей не ограничивает объем строк/HTML и может сохранять множество промежуточных версий большого блока.

Измерение самого highlighter, 10 разных окончаний на блок, без DOM/layout: медиана 3.6 мс для 100 строк, 10.9 мс для 400 строк, 25.8 мс для 1000 строк. Это простой XBSL, native macOS Chrome, не худший случай. 25.8 мс уже больше бюджета одного кадра 60 Гц до учета рендера страницы.

Исправление: сохранять завершенные Markdown-блоки, обрабатывать активный блок с ограниченной частотой; вынести дорогое выделение токенов в Worker с отбрасыванием устаревших результатов; добавить byte budget и предельный размер блока. Сохранить проверенную грамматику и цвета xbsl.io.

### F10 [P2] Нативные вопросы app-server не обрабатываются

Место: `src/codexRuntimeController.ts:2481`; метод присутствует в `scripts/fixtures/app-server/0.153.4.json`.

`item/tool/requestUserInput` не распознается как approval или MCP elicitation. Handler логирует unsupported request и возвращает `{}`. На искусственном запросе с вопросом и вариантами подтвержден именно такой ответ; UI вопрос не получает. Собственный механизм уточнений из текста не заменяет этот протокольный запрос.

Это ограничение покрытия возможностей, не доказанная регрессия исключительно версии 0.153.4. Текущие protocol tests проверяют 15 используемых методов, а не все возможности runtime.

Исправление: отдельный тип запроса/ответа, форма вопросов, привязка к request/item/turn/chat; cancel, timeout, server resolution и secret fields; контрактные fixtures. Не отвечать пустым успешным result на неизвестную обязательную интеракцию.

### F11 [P2] Approval визуально модальный, но клавиатурный фокус остается за ним

Места: `media/chat.js:607`, `media/chat.js:3320`, `media/chat.js:1391`.

После snapshot с pending approval восстанавливается фокус textarea. У overlay есть `role=dialog` и `aria-modal`, но нет соответствующего управления фокусом и изоляции фоновых контролов.

Браузерный тест подтвердил: диалог виден, `document.activeElement` остается textarea вне него. Это затрудняет подтверждение с клавиатуры и оставляет активным фон вместо ожидаемого диалога.

Исправление: первоначальный фокус на безопасном действии, focus trap, недоступный для взаимодействия фон, возврат фокуса после закрытия. Это проверяется отдельно от наличия ARIA-атрибутов. Полная WCAG-сертификация в данном ревью не проводилась.

## Дополнительные риски и технический долг

Ниже не выдаются за воспроизведенные производственные инциденты:

- Команды чата часто не несут исходный `chatId`; `ChatPanelManager` берет текущий активный чат. Нужен тест переключения A/B при задержке команд между sidebar и chat webview, в том числе возврата ошибок отправки. Иначе возможна ошибочная адресация запоздалого действия.
- `startNextQueuedPrompt()` удаляет сообщение из очереди до успешного запуска. Нужны состояния queued/dispatching/accepted/failed и повтор с сохранением текста; отдельный тест падения между dequeue и turn/start.
- История хранится общим JSON. Trailing debounce 600 мс не имеет max-wait; непрерывные deltas могут долго откладывать запись. Immediate saves сериализуют все чаты и ставятся в цепочку без coalescing. Нужны durability policy, bounded write queue и восстановление после сбоя. JSONL сам по себе не решает ни scroll, ни повреждение/конкурентную запись: журнал событий и snapshot требуют отдельного дизайна.
- `BrowserRuntimeService.prepareMcpServer()` пишет config/init/artifacts в общий `<configRoot>/browser`. Проверить раздельность по профилю/workspace и гонки двух IDE; одинаковое имя конфигурации не должно смешивать настройки текущих сеансов.
- `saveMcpServer()` откатывает весь `config.toml` к прочитанному snapshot при ошибке. Без serialization/locking параллельное изменение другого поля может потеряться. Это требует теста конкурентного изменения, а не только save happy path.
- Ripgrep reinstall удаляет destination версии до проверки нового файла (`src/ripgrepInstallerService.ts:79`). Предпочтительны staging, проверка до переключения, backup предыдущей установки.
- Markdown реализован ручным line/regex parser. В частности numbered lists проходят через общий `<ul>` (`media/chat.js:4073`), а полноценный CommonMark/GFM контракт не обеспечен. Parser links tests не равны UI tests.
- Native diff строится из фрагментов patch, включая строки `@@`, а не из двух полных ревизий файла (`src/diffArtifactService.ts:61`). Это просмотр фрагментов, не основание для безопасного revert целого файла.
- В XBSL external-asset fallback не включена загрузка highlighter (`src/webviewHtml.ts:53`). Проверить сценарий доступного inline chat.js и недоступного preload: успешно показанный чат еще не гарантирует нужную подсветку.
- UI roadmap в соседней документации все еще описывает состояние `0.1.74`; README содержит ссылки на `0.1.87`. Статусы выполненности нужно сверить с воспроизводимыми проверками, не заменять автоматически отметками «готово».

## UI/UX оценка

Использован навык Impeccable: technical audit. Оценка предварительная, по коду и описанным браузерным fixtures, не по полной матрице устройств.

| Область | Балл / 4 | Основание |
|---|---:|---|
| Доступность | 2 | Есть labels и focus styles, но approval не удерживает фокус; menu keyboard contract неполный |
| Производительность | 1 | Воспроизведенные замены скроллера, полный snapshot, синхронная подсветка |
| Адаптивность | 2 | Есть breakpoints и ограничение окон; полная streaming/zoom/long-content матрица отсутствует |
| Темы | 3 | Используются VS Code tokens и light/dark XBSL темы; high contrast проверен не для всех поверхностей |
| Целостность реализации | 2 | Предметная модель понятна, но presentation зависит от окна и ручных render signatures |
| Итого | 10 / 20 | Требуется существенная работа над устойчивостью |

Integrity verdict: визуальная система предметная, но технический контракт стабильного рабочего интерфейса сейчас не выдерживается. Механический detector для шести chat/sidebar/settings JS/CSS файлов вернул `[]`; это не противоречит поведенческим ошибкам, которые он не проверяет.

Что сохранить: тихую рабочую компоновку, единый composer, turn summary, раскрываемые worklog, границы клиентских uploads и серверных файлов, native IDE opening, runtime-driven model catalog, proxy только на нужных серверных соединениях. React не требует менять эту продуктовую модель.

## Решение по React

### Что меняем и что оставляем

В браузере пользователя остается тот же Theia WebviewPanel. Внутри него работает локально поставляемый React bundle. На сервере остаются extension host, существующие сервисы, app-server и MCP. Не нужны отдельный публичный сайт, Next.js/SSR, дополнительный сетевой порт, CDN или Node на компьютере пользователя.

Предлагаемый состав:

- React + TypeScript, сборка существующим esbuild. Сначала chat panel; sidebar/settings позже.
- Нормализованный store с подписками на отдельные сущности. Не передавать целый snapshot через один React Context на каждый token. При использовании внешнего store нужны стабильные cached snapshots согласно [контракту React](https://react.dev/reference/react/useSyncExternalStore).
- Typed bridge adapter: snapshot/patch/command/result; `chatId`, ревизия, ID запроса и поколение подключения; resync после разрыва. Серверное состояние авторитетно, draft/scroll/selection остаются локальными.
- Отдельные компоненты TranscriptViewport, Message, TurnRun, Worklog, Diff, Composer, Queue, ApprovalDialog. Стабильные ID, а не индексы массива, используются как keys.
- Виртуализация с динамической высотой и проверенным anchoring. [TanStack Virtual имеет пример chat с prepend и streaming](https://tanstack.com/virtual/latest/docs/framework/react/examples/chat); его рассматриваем кандидатом, не гарантией готового решения для вложенных diff и Element. Зафиксировать версию после прототипа в целевом браузере.
- [react-markdown](https://github.com/remarkjs/react-markdown) + [remark-gfm](https://github.com/remarkjs/remark-gfm) для структуры Markdown; custom renderer локальных ссылок сохраняет server-side IDE opener, raw HTML не включать. XBSL/YAML грамматику сохраняем; кэш и scheduling подсветки меняем отдельно.
- CSP-compatible Worker для тяжелой подсветки: проверка оболочки Element подтвердила self-contained Blob Worker с отдельным `worker-src blob:`. На HTTP нельзя требовать Service Worker или обязательную загрузку worker-файла через `asWebviewUri`; нужен полный inline bootstrap и fallback с лимитами. Полный highlighter еще требует проверки. Никакого unrestricted raw HTML и eval.

### Обязательные инварианты

1. Новое содержимое обновляет данные всегда; автопрокрутка включена только когда пользователь следует за концом.
2. При чтении истории новые события не меняют scroll container, composer и выбранное место чтения.
3. Добавление сверху сохраняет anchor item ID и смещение внутри элемента; поздняя подсветка и изменение высоты учитываются тем же механизмом.
4. Turn grouping не зависит от того, попал ли родитель в страницу. Длинные раскрытые children не раздувают DOM бесконтрольно.
5. Поиск по истории работает на всей истории, а не только среди DOM-узлов виртуального окна.
6. Дубликаты patches идемпотентны; пропуск/устаревшая ревизия обнаруживаются; события завершения и ошибки не теряются при batching.
7. Очередь, draft, вложения и approvals не теряются при переключении renderer или reconnect. Старый renderer доступен как временный rollback, не как второй конкурентный владелец DOM.

### Порядок внедрения

| Этап | Результат | Условие перехода |
|---|---|---|
| 0. Regression baseline | Перенести fixtures этого аудита в репозиторий и UI CI | Тесты демонстрируют F01/F06/F07/F11 на старом коде |
| 1. Стабилизация | Исправить F01-F04 и stop lifecycle, убрать дубли snapshot | Нет потери истории/профиля; скроллер стабилен во время stream |
| 2. Data contract | Patch adapter, entity store, revision/resync, metrics | Сверка результата с серверным snapshot и тесты задержек/дубликатов |
| 3. React chat | Transcript и composer под feature flag, общий backend | Паритет Markdown, links, diff, queue, steer, approvals, attachments |
| 4. Виртуализация и подсветка | Динамические измерения, bounded cache, Worker/fallback | Длинная история + stream + раскрытие diff проходят acceptance |
| 5. Переключение | Новый renderer по умолчанию, удаление старого после проверки | Windows/Linux Element acceptance и воспроизводимый UI gate |

Не совмещать в одну поставку React, замену формата истории и большой новый Git workflow: это усложнит диагностику регрессий. Сначала восстановить корректность, потом оптимизировать объем данных, затем менять renderer. Увеличение окна с 120 до 200/1000 само по себе F01 не устраняет и может увеличить стоимость полной перерисовки.

## Что добавить относительно Desktop

Речь о полезном поведении, не о копировании внутренних компонентов Desktop. Новая версия app-server не добавляет эти UI-функции автоматически.

| Приоритет | Возможность | Адаптация для Element |
|---|---|---|
| После стабилизации | Review workspace/last turn, комментарий к строке | Привязать замечание к file/revision/range; использовать IDE bridge. Сначала read-only diff и обратная связь, потом stage/revert с проверкой текущего содержимого |
| После стабилизации | Нативные вопросы и решения runtime | Реализовать F10, не распознавать все интеракции по текстовым маркерам |
| После стабилизации | Поиск по чатам/истории, переход к результату | Поиск на серверной модели, загрузка окна вокруг item ID; browser find не видит выгруженные сообщения |
| Следующий срез | Browser test artifacts | Видимые screenshot/console/network результаты, открыть артефакт, повторить проверку; явно показывать, что браузер работает на сервере |
| Следующий срез | Project actions | Capability-checked адаптер штатных команд Element и readiness/timeout LSP; обычный terminal/task может быть запрещен режимом бандла. Конфигурация per project, а не глобальная строка shell |
| Позже | Разветвление диалога и несколько задач | Сначала versioned thread contract и понятное состояние каждого запуска. Отдельный чат не означает отдельный workspace |
| Позже | Git worktrees / параллельные изменения | Проверить совместимость регистрации проектов Element, LSP, сборки и путей. Нельзя обещать независимые запуски, просто создав вторую git checkout |

Desktop reference: официальный [review workflow](https://learn.chatgpt.com/docs/code-review?surface=app) поддерживает области сравнения, комментарии и Git-действия; [local environments](https://learn.chatgpt.com/docs/environments/local-environment) описывает project actions; [worktrees](https://learn.chatgpt.com/docs/environments/git-worktrees) отделяют параллельные изменения. Для Element это ориентиры, а не готовый контракт интеграции.

## Проверки и ограничения

В этом ревью прошли: `npm run check`, `check:models`, `check:protocol`, `check:mcp-elicitation`, `check:markdown-links`, `check:transcript-window`, `eval:context`, `git diff --check`. Production build и release заново не выпускались.

Локальные воспроизводители находятся рядом с репозиторием, в `../local-codex-temp/`:

- `review-chat.cjs` / `review-chat-result.json`: реальный `media/chat.js` и `chat.css`, fake webview bridge, synthetic snapshots. Scroll, выделение, stale completion, streaming links, grouping boundary, approval focus.
- `review-highlight.cjs` / `review-highlight-result.json`: реальный поставляемый highlighter, уникальные потоковые версии XBSL-блока.
- `review-backend.cjs` / `review-backend-result.json`: реальные compiled services, mock VS Code API, изолированная история, управляемый тестовый процесс, profile fallback и unsupported user input. Настоящий app-server для этих проверок не запускался.

UI среда: native macOS, headless Chrome `152.0.7977.76`, viewport 1280x850. Не Docker/QEMU. Stream fixture использует 61 сообщение и обновления примерно каждые 25 мс; сетевой канал Theia не входит в измерение. Основной scroll test выполняется без Shiki, чтобы отделить lifecycle ошибки от стоимости подсветки. Замеры JS handler не равны frame time и не доказывают плавность на сервере пользователя.

Архитектурно рассмотрены runtime/controller, transport/process lifecycle, state/history, chat/sidebar/settings webviews, integrations/browser, attachments, identity, IDE bridge, context/indexing, deployment/CI. Наиболее подробно проверены пути, перечисленные в находках. Это не доказательство отсутствия ошибок в каждой ветке всех сервисов. Реальная многопользовательская Theia, Windows server session, browser auth, proxy/network, service-account permissions, длительная работа и полная theme/zoom/screen-reader матрица в этом ревью не проверялись.

### Acceptance для следующего среза

- 1000 и 10000 смешанных transcript items; 20-50 delta/с; обычный и быстрый scroll в обе стороны.
- 0 замен scroll container при delta; 0 потерь draft/selection; completed/error видны без ручного reload.
- При updates вне viewport anchor не дрейфует; целевой допуск 2 CSS px после стабилизации layout. Для пользовательского раскрытия большой карточки задается отдельное ожидаемое поведение.
- Новые ссылки кликабельны до завершения stream; таблицы, numbered lists, code и diff сохраняют структуру.
- Проверки с 100-300 мс задержки bridge, дубликатами, reconnect, переключением A/B, отменой, очередью и загрузкой файлов.
- Раздельные метрики JS/render/layout/paint, long tasks и bytes/sec. Цель: большинство кадров в бюджете 60 Гц; отсутствие повторяющихся long tasks >50 мс на согласованной тестовой машине. Порог не считается выполненным по одному среднему значению.
- Ограниченный DOM и byte-budget кэшей, отсутствие постоянного роста памяти после повторного обхода истории.
- Approval только с безопасным фокусом; полное прохождение клавиатурой; narrow/light/dark/forced-colors/zoom 150-200%/reduced-motion.
- UI test job на pull request/push до release; текущий release workflow проверяет source/protocol, но не запускает браузерный scrolling harness.

Для UI-работы по этому отчету: `$impeccable optimize` для F01/F05/F09, `$impeccable harden` для F06/F07/F11, повторный `$impeccable audit`, в конце `$impeccable polish`. Эти этапы можно выполнять отдельно или последовательно; оценку следует пересчитать после исправлений.
