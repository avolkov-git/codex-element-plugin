# IDE-сессии 1C Element MCP

Версия плагина: `1.0.5`, ветка `master`.
Протокол: IDE sessions v1 из 1C Element MCP 0.23.0 и новее; подробная диагностика Console доступна с MCP 0.23.1.
Bundled Codex: 0.154.0.

## Когда включается

Плагин не запускает и не устанавливает внешний MCP. В настройках должен быть включён один HTTP-сервер
с адресом `/mcp`, соответствующим `codexElement.elementMcpUrl`. Поддерживаются только loopback-адреса
`127.0.0.1`, `localhost`, `[::1]`. Удалённая автоматическая передача Console credentials не поддерживается.
Само наличие исходников MCP 0.23.0 не доказывает, что эта версия запущена: перед созданием сессии проверяется `/api/status`.

Без такого подключения менеджер не отправляет Console credentials и не создаёт сессии.
История, авторизация Codex, встроенный Playwright MCP и остальные MCP не зависят от доступности этой службы.

## Источник контекста

Используются штатные параметры Element IDE: адрес Console, её авторизация, `1C.projectId`,
`1C.applicationId` и локальные `workspaceFolders`. Без обязательных UUID и существующих каталогов
сессионное подключение не разрешается. Имя приложения, URL из чата, ID из YAML и Git-репозиторий
не используются как замена штатным идентификаторам.

MCP проверяет в Console связь приложения и проекта. Выбор локального проекта среди нескольких
кандидатов внутри workspace нужен для чтения исходников, но не меняет цель операций Console.
Параметры Console не передаются модели.

В Element 9.2.4 IDE может открывать группу проектов: тогда `1C.projectId` отличается от
`application.project.id`. Плагин принимает такой ответ только с подтверждением MCP
`project_match_kind: group` и `application_project_group_id`, совпадающим с ID текущей IDE.
MCP проверяет штатный `group-id` проекта, тип группы и общее пространство через Console.
Необходим MCP 0.23.2 или новее: версия 0.23.1 ещё отвергает этот сценарий.
Идентификаторы приложения, сессии и workspace при этом не подменяются.

## Время жизни

Один экземпляр менеджера принадлежит одному extension host с контекстом окна IDE. Чаты этого окна
используют одну сессию, пока её идентичность неизменна. Второе окно получает новую сессию независимо
от того, открыто ли в нём другое приложение или то же самое.

1. Менеджер проверяет конфигурацию MCP, официальный контекст, версию сервера и локальный CSRF token.
2. Создаёт сессию через `POST /api/integrations/ide-sessions`.
3. Добавляет временный header override к существующему имени MCP, не создавая второе подключение.
4. Через MCP проверяет `get_managed_actions_status` и `get_current_application`, включая ожидаемые ID.
5. После подтверждения области показывает готовность и продлевает lease независимо от изменения Git-статуса.

Настройки другого окна не перезаписываются. Перезапуск app-server использует живую сессию снова,
но её заголовок устанавливается и проверяется заново. Смена идентичности, expiry и потеря управляющей
сессии аннулируют старый runtime и ожидающие подтверждения. Автоматический повтор write или перенос
активной операции на новую цель не выполняются.

Опоздавший ответ создания после смены контекста не активирует старую сессию: она отзывается.
При закрытии IDE отзыв выполняется best effort; при аварийном завершении остаётся серверный TTL.
Тайм-аут revoke не доказывает отмену уже отправленной операции Console. Сначала проверьте её результат
read-only инструментом; не повторяйте execute автоматически.

## Секреты и границы

`mcp_token` нужен только HTTP-транспорту MCP; `control_token` только renew/revoke.
Они не записываются в общий профиль, workspace state, аргументы команд, подсказки модели или UI.
Секрет MCP передаётся через приватную переменную окружения app-server; `process.env` extension host не меняется.
Временные overrides дополняют настройки встроенного браузера, а не заменяют их.

В 0.154.0 используется одна частичная TOML-таблица `mcp_servers={...}` в аргументе `-c`.
Она объединяется с базовой конфигурацией, поэтому существующие HTTP headers и остальные MCP не нужно
копировать в аргументы процесса. Такая запись поддерживает имена с точками; кавычки в пути CLI-ключа
не работают как кавычки TOML. Browser overrides применяются после этой таблицы.

Для shell-команд `shell_environment_policy.set.ELEMENT_IDE_MCP_SESSION_TOKEN=""` очищает значение,
сохраняя действие существующих `exclude`. Новая настройка `filters` в этом runtime отключает legacy
exclude-массивы, поэтому плагин её не использует. Для настроенных stdio MCP значение дополнительно
очищается в их `env`: явное `env_vars` иначе может передать токен независимо от shell policy.
Переменная в таких дочерних процессах может существовать, но быть пустой. Явное окружение команды
и исследование родительского процесса не покрываются этой защитой.
Использование зарезервированной переменной для другого HTTP MCP блокирует сессионный запуск.

Runtime также отправляет настроенные HTTP headers на same-origin OAuth discovery endpoints.
Это особенность штатного MCP-клиента, проверенная на локальном стенде, а не отдельная передача токена
со стороны bridge. Автоматическая привязка поддерживается только для доверенного loopback MCP.

Это изоляция клиентов и целей операций, не защита от администратора ОС или агента с произвольным
локальным выполнением. Такой процесс может исследовать окружение или память процессов с теми же правами.
Сетевые и пользовательские границы самого сервера остаются обязательными.

В настройках нельзя добавить второй alias того же endpoint или сохранить session token как bearer token.
При ошибке привязки MCP не переключается незаметно на подключение без заголовка. Старый общий endpoint
`/api/integrations/element-console` больше не используется.

## Обновление и диагностика

- MCP старее 0.23.0 или отсутствующий session endpoint: обновить MCP отдельно, затем повторить проверку.
- Нет штатного application/project ID: открыть IDE нужного приложения, не вводить UUID из переписки.
- HTTP 400: известные причины валидации показываются в настройках и логе Codex без исходного тела ответа,
  путей и секретов. Для неизвестной причины нужен журнал MCP за время подключения.
- Workspace недоступен MCP: проверить права процесса MCP и, если он работает в контейнере, доступность
  переданного IDE пути внутри контейнера. Доступность папки плагину не доказывает её доступность MCP.
- MCP 0.23.1: известные `code` отображаются по-русски в статусе подключения и логе.
  `console_authentication_failed` означает отказ проверки авторизации через список пространств;
  `console_application_failed` — ошибку чтения или проверки карточки приложения.
  Для Console HTTP 401 предлагается проверить авторизацию, для 403 — права, для 404 — выбранный сервер
  и `1C.applicationId`. Console HTTP 404 передаётся MCP как HTTP 502 и не означает отсутствие session endpoint.
- `application_project_missing`, `application_project_invalid`, `application_project_mismatch`:
  соответственно отсутствующий ID проекта, некорректный UUID и подтверждённое несовпадение проектов.
  Неудачное чтение приложения не называется несовпадением проектов. Чужую цель из чата плагин не подставляет.
- В MCP 0.23.0 общий отказ «Console не подтвердила связь приложения и проекта» ещё может означать ошибку чтения.
  Для точной диагностики обновите MCP до 0.23.1. Неизвестные коды и произвольные сообщения сервера
  не выводятся; нужен журнал MCP за время подключения.
- Сессия истекла или MCP перезапустился: повторить проверку в настройках. Для записи выполнить новый prepare
  и заново подтвердить точную цель.
- `migration_required`: оператор должен явно сохранить политику schema 2 в UI MCP. Плагин этого не делает.
- `can_prepare=false`: подключение может быть исправным, но управляемые действия выключены оператором.

## Проверки и ограничения

Серверный контракт проверяется исходными `tests/test_ide_sessions.py`, `tests/test_actions.py`,
`tests/test_ui.py` в репозитории MCP. Подмена ответов Console в этих тестах не означает проверку живого сервера.
Тесты плагина покрывают lifecycle, заголовки, конфигурацию и очистку подтверждений.
Отдельный smoke запускает настоящий bundled app-server против изолированного MCP-стенда, без обращения к модели.

После запуска MCP пользователем `GET http://127.0.0.1:9900/api/status` подтвердил версию 0.23.0.
Endpoint IDE-сессий существует; `initialize` и `tools/list` показали 73 инструмента, включая оба инструмента
проверки привязки. Настоящий bundled app-server на macOS вызвал `get_managed_actions_status` и
`get_current_application` этого MCP: без IDE-сессии сервер вернул `workspace_scope=missing`,
`can_prepare=false` и `status=not_available` соответственно.

Изолированный smoke с настоящим app-server прошёл на Darwin arm64 и Linux arm64: два процесса с общим
профилем, разные токены, reload/restart, HTTP headers, сохранение остальных MCP и очистка окружения
дочерних процессов. В Windows/Linux release CI добавлен тот же smoke для целевых x64-бинарников;
его запуск на Windows в рамках этой задачи не подтверждён.

Проверка двух настоящих окон Windows/Element с установленным MCP 0.23.0 пока не проведена.
Для создания живой сессии нужны штатные ID и авторизация из Element IDE; тестовые ID вместо них не передавались.
Операции записи в опубликованные приложения не выполнялись.

Перед выпуском необходимо проверить два окна Element: разные приложения, затем одно приложение;
scope и approvals не должны смешиваться. Первый write-smoke проводить только в отдельном тестовом
приложении с отдельным согласием: prepare, показ точной цели, подтверждение, execute, read-only сверка.

## Изменения для следующего релиза

- Общий handoff заменён отдельной IDE-сессией на окно.
- Привязка HTTP MCP переносится в process-local configuration и не сохраняется в профиле.
- Добавлены heartbeat, обработка expiry, revoke и защита от запоздавших ответов.
- Изменение контекста останавливает старые операции и отменяет старые подтверждения.
- В настройках появился статус привязки и повторная проверка; дублирующее подключение MCP блокируется.
- Права на управляемые изменения и миграция политики остаются под управлением оператора MCP.
