# Третий этап: правила и последствия изменений

Цель этапа: дать агенту требования к выбранным модулям и проверяемые сведения о
последствиях правок. Это не новый компилятор, не тестирование бизнес-логики и не
разрешение автоматически исправлять все найденные места.

## Правила перед запросом

Существующий `.local-codex/rules.md` сохраняет прежнюю роль общепроектных правил.
Он подключается отдельно от дополнительных правил; в проектных маршрутах его
нельзя вытеснить дополнительными правилами при распределении общего бюджета.
Переключатель правил чата действует на оба источника. Общий чат не получает их
автоматически.

Дополнительные файлы находятся непосредственно в `.local-codex/rules/*.md`.
В начале нужен YAML frontmatter. Например:

```markdown
---
paths:
  - DOMRF/Start/СтруктураПредприятия/**
elementKinds:
  - КомпонентИнтерфейса
---
Перед изменением обработчика проверь его привязку в YAML.
Сохраняй существующий порядок проверок доступности действий.
```

`paths` и `elementKinds` необязательны по отдельности, но нужен хотя бы один
селектор. Каждый селектор является непустым списком строк. Между списками действует
И на одном и том же файле, внутри списка действует ИЛИ. Имя типа элемента должно
точно совпадать с `ВидЭлемента` в YAML проекта.

Поддерживаемые пути: точное имя файла, `каталог/**`, `*.xbsl`, `каталог/*.xbsl`,
`**/*.xbsl`, `каталог/**/*.xbsl`; аналогично для других расширений. Сопоставление
регистрозависимое. Отрицания, фигурные и квадратные скобки, `?` и произвольные glob
выражения не поддерживаются. Некорректное правило пропускается с предупреждением,
а не превращается в правило для всех файлов.

Цели берутся из проектного контекста запроса и актуального отчёта предыдущей
проверки. Без подтверждённых файлов дополнительные правила не подключаются.
Чтение файла, список символов и явное выделение редактора также передают пути
целей. Источник привязан к своему workspace: одноимённый файл в другом корне
не подтверждает применимость правила. В запросе сохраняются селекторы и список
совпавших файлов, чтобы модель не применяла адресное правило ко всему проекту.
Для XBSL тип элемента берётся из парного YAML, в том числе для `.Объект.xbsl`.
Пути проверяются относительно текущего workspace; симлинки ниже его корня не
используются. Правила перечитываются, включая несохранённый текст редактора.

Лимиты дополнительных правил: 64 файла, 32 КиБ на файл, 256 КиБ чтения суммарно,
12 000 символов текста в контексте. Общепроектные правила имеют отдельные прежние
лимиты. Предупреждения и усечение записываются в лог.

## Проверка после ответа

1. Перед `turn/start` обычного проектного запроса с правом записи снимаются хеши
   YAML/XBSL из доступного индекса и текущий кеш диагностик IDE. Планирование,
   режим чтения и общие чаты этот цикл не запускают.
2. После нормального завершения запроса индекс перечитывается с проверкой хешей.
   Учитываются и изменения через команды, а не только события `fileChange`.
   Открытые несохранённые документы остаются источником актуального текста.
3. Изменённые XBSL проверяются штатным AST, YAML разбираются структурным парсером.
   В парных файлах проверяются обработчики. По именам объявлений изменённых модулей
   отбираются потенциально связанные файлы; AST различает вызов и ссылку на метод
   (`MethodRef`) и сохраняет исходное обращение с получателем.
4. Доступный Language Server уточняет цели через публичные провайдеры IDE.
   Пустые, неоднозначные, устаревшие и выходящие за границы проекта ответы не
   считаются подтверждением. Второй Language Server не запускается.
5. Результат появляется в обычном журнале действий чата. Диагностики IDE берутся
   только для изменённых и связанных файлов. Отмечается, было ли сообщение в
   исходном кеше, но не утверждается, что ошибку внёс агент.
6. Отчёт передаётся в следующий пользовательский или очередной запрос только
   после проверки профиля, workspace, состава индекса и хешей. Кеш диагностик
   IDE перечитывается даже при неизменных исходниках. Устаревший отчёт удаляется.

Очередь сообщений ждёт завершения ограниченной проверки. Новый ручной запрос
может отменить её. Отмена, остановка runtime, смена пользователя, проекта или
истории не позволяют позднему результату попасть в другой сеанс.

Прежний скрытый повторный запрос «исправить все ошибки IDE» удалён. Проверка
ничего не редактирует и не запускает дополнительный запрос модели. Исправления
выполняются в рамках следующего запроса пользователя, с учётом его задачи.

## Значение результата

- `ast`: штатный парсер подтвердил синтаксическое вхождение, но не цель вызова.
- `structural`: имя обработчика YAML совпало с объявлением парного XBSL.
- `candidate` / `unresolved`: требуется проверка; наследование и встроенные
  обработчики не позволяют объявить такое место ошибкой только по локальному поиску.
- `lsp`: провайдер вернул единственное определение, и его файл/диапазон проверены.
  Это не доказывает завершение серверной переиндексации или отсутствие регрессии.

Отчёт показывает наблюдаемые изменения. В них могут быть ручные правки или работа
другого чата, поэтому авторство не приписывается агенту. Исчезновение файла из
ограниченного индекса не считается доказанным удалением: файл мог стать пустым,
слишком большим или недоступным.

Проверка ограничена 400 файлами, 2 МиБ исходников плюс повторное чтение для
подтверждения, 40 разборами AST и 20 обращениями к LSP. На анализ отведено до
10 секунд, включая резерв финальной проверки. Снимки индекса имеют отдельный
таймаут 8 секунд; проверка кешированного отчёта перед запросом занимает не более
2 секунд. В отчёт попадает до 16 000 символов. Пропуски отмечаются явно.
Граница межмодульного поиска определяется ближайшим `project.yaml`; без него
поиск ограничивается тем же каталогом и помечается неполным.

Это не полная база ссылок компилятора. Изменения типов, схем данных и поведения
методов требуют сборки и тестов приложения. Диагностика после правки сама по себе
не доказывает, что раньше её не было. Пустой кеш IDE не означает успешную проверку.
Гранулярность исходного снимка: файл, а не изменение тела отдельного метода.
Поэтому среди кандидатов могут быть вызовы неизменённых методов того же модуля;
без LSP они не объявляются точными зависимостями изменённого метода.

## Проверки

```sh
npm run check
node --test tests/project-change-analysis.test.cjs tests/project-change-review.test.cjs tests/project-change-runtime.test.cjs tests/scoped-project-rules.test.cjs
node scripts/evaluate-project-changes.cjs --project /path/to/privet-dom-app --jar /path/to/appengine-lsp.jar --output /tmp/project-changes-evaluation.json
```

Проверка на реальном проекте выполняется на временных копиях. Результаты:
[project-changes-evaluation.json](project-changes-evaluation.json).
AST используется настоящий; работающий Language Server в тестовой IDE пока
недоступен. Его ответы и гонки проверяются отдельными тестовыми сценариями, что
не заменяет сквозную проверку в Element на Windows Server. Качество итогового
кода или ответов модели этим прогоном не измеряется.

### Локальный результат

Проверка 14 октября 2026 года: 838 тестов прошли без пропусков. Новый прогон на
`privet-dom-app`, commit `5f3e72ed3afed7d04b9af8b700fe5094c847ee32`, прошёл 6/6
сценариев с настоящим AST. Во временные копии вошли 607 отслеживаемых YAML/XBSL
и общий файл правил; это не полная развёрнутая сборка приложения.

| Сценарий | Проверенное наблюдение | Отчёт, символов |
| --- | --- | ---: |
| Переименование только XBSL-обработчика | Привязка YAML стала неподтверждённым кандидатом | 3489 |
| Согласованное переименование YAML и XBSL | Все три обработчика компонента структурно сопоставлены | 3354 |
| Нарушение синтаксиса XBSL | Получена штатная синтаксическая диагностика | 3945 |
| Переименование метода общего модуля | Сохранён ожидаемый входящий вызов с путём и строкой | 15094 |
| Переименование метода, используемого через `MethodRef` | Сохранена ожидаемая ссылка на метод | 15094 |
| Без изменений | Нет замечаний, чтений исходников и вызовов AST внутри анализатора | 1535 |

Все ожидаемые сведения сохранились после форматирования отчёта; лимит 16 000
символов не срезал проверяемые места. Адресные правила выбирались без постороннего
правила, общепроектные правила сохранялись. Сделано 25 вызовов штатного AST;
22 обращения к LSP получили явный ответ о недоступности. Поэтому все пять
отчётов о правках остались частичными, а не были объявлены полной проверкой.
Исходный тестовый проект не изменён.

Для общих модулей найдено по 36 наблюдений: это кандидаты уровня изменённого
файла, а не 36 доказанных регрессий. Следующий шаг оценки качества требует живой
IDE и проверки выполненных агентом задач, включая сборку и поведение приложения.
