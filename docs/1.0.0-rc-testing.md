# Установка и проверка 1.0.3

Стабильный релиз 1.0.3 выпущен на основе прошедшего пользовательскую проверку кандидата 1.0.2-rc. Руководство и исторические разборы RC применимы к бандлу 1C Element 9.2.4-6. Выбирайте пакет по ОС сервера: Windows x64 или Linux x64. Веб-интерфейс остается внутри IDE, Codex и Chromium работают на сервере.

## Установка и откат

1. Сохраните открытые файлы. Остановите серверный процесс IDE (Theia backend) средствами администрирования Element и сохраните копию установленного каталога плагина вне `/plugins`. Закрытие вкладки браузера или перезапуск одного plugin host не заменяют остановку backend.
2. Сделайте резервную копию config root (`Codex: Открыть папку логов` показывает его каталог логов). Не удаляйте `users`.
3. Распакуйте релиз и замените содержимое установленного каталога плагина в `/plugins`, сохранив его имя (например, `codex-element` или `codex-plugins`). `package.json`, `dist`, `media` и `resources` должны находиться в его корне. Не держите две версии с одинаковым ID плагина в этом каталоге.
4. Запустите серверную IDE и откройте ее в браузере. В журнале должна появиться строка `initializing(codex-element-v1@1.0.3`, а в настройках плагина версия `1.0.3`.
5. Для отката верните сохраненный каталог предыдущей версии и перезапустите IDE. Релиз не изменяет исходные legacy `workspaces/*/chats.json`.

Изменения, сделанные в чатах RC после переноса, не появляются в старой 0.1.89. Сохраните новый каталог `users/<userKey>/projects/` при откате. Нельзя переносить весь config root от другого пользователя или заменять им текущий без проверки владельцев.

## Пустая панель до входа в Codex

При проверке Windows-стенда 1.0.2-rc в консоли браузера обнаружены HTTP 404 для `resources/icons/codex.svg` и ошибки `command 'codexElement.openLogs' not found` / `command 'codexElement.openSettings' not found`.

Серверный журнал от 9 сентября 2026 года установил причину: Theia искала `package.json` и иконку в удаленном `plugins/codex-element-1.0.1rc`, хотя новая поставка находилась в `plugins/codex-element`. В `ide-log-0.log` строки 453 и 634 содержат `Failed to initialize element-ai.codex-element-v1 plugin` с `ENOENT` для старого `package.json`; строки 392 и 573 содержат ту же ошибку для иконки. Код 1.0.2-rc до активации не дошел.

Backend запустился в 23:33:57 и прочитал прежний список плагинов. В 00:02 и 00:03 запускались новые plugin host, но не backend; старый путь сохранился в его реестре. Требуется остановить и запустить серверную IDE, чтобы Theia перечитала `/plugins`. Перезапуск всего экземпляра сервера Element тоже затрагивает IDE, но прерывает работу других пользователей и приложений: его нужно согласовать. Не исправляйте этот случай созданием второй копии плагина по старому пути, очисткой истории или ослаблением проверки пользователя Console.

Журнал Theia находится в `<instanceRoot>/logs/ide/<ideId>/ide-log-0.log`; после ротации проверьте соседние `ide-log-*.log`. Это следует из `EmbeddedIdeLayout.logsRoot`, `EmbeddedIdeProcessLauncher.getLogRoot` и `EmbeddedLoggerProcessor` бандла 9.2.4-6. ID текущей IDE указан в адресе браузера после `/ide/api/v1/`.

Нужна первая ошибка со стеком после `Activating plugin 'Codex for 1C: Element' failed:` или `Failed to initialize element-ai.codex-element-v1 plugin.`. Строка о старте всех плагинов не подтверждает успешную активацию Codex. HTTP 404 для иконки проверяйте отдельно: Theia регистрирует путь ресурсов до активации. Сохраните тело ответа 404, чтобы отличить отсутствие записи плагина от отсутствующего файла.

`npm run check:startup` проверяет загрузку собранного `dist/extension.js`, регистрацию команд и sidebar, выдачу первого HTML и ответ без настроек Console/MCP через тестовый VS Code API. Для проверки готовой поставки задайте `CODEX_TEST_PLUGIN_ROOT` с ее корнем. Тест не запускает Windows-бинарники и не заменяет проверку активации внутри Element. В следующем журнале Windows-стенда, с отметкой `2026-09-08T21:33:40Z`, плагин завершил активацию за 60 ms и получил `Sidebar webview ready`. Новый отказ произошел уже при проверке Console.

## Возобновление длинной истории

В журнале от 10 сентября 2026 года после успешного входа первая отправка
завершалась сообщением `Codex backend output exceeds 8388608 bytes per line`,
затем `thread/resume: JSON-RPC client disposed`. Причина находилась в плагине:
возобновление запрашивало все серверные turns одним ответом и превышало лимит
транспорта. Ответы `resume` и `fork` теперь запрашиваются без turns; история
на сервере и локальная лента сохраняются. Подробнее: [контракт runtime](app-server-0.153.4.md#возобновление-длинного-диалога-в-rc).

После обновления поставки перезапустите серверную IDE и отправьте сообщение
в тот же длинный диалог. Ожидаются `thread/resume completed: ...; excludeTurns=true`
и `turn/start accepted`, без остановки app-server. Отдельно проверьте
разветвление этого диалога. Не удаляйте чаты, `auth.json` или каталог `users`.

Автоматические проверки: `npm run check:runtime`, `npm run check:protocol`
и smoke-test настоящего бинарника без авторизации. Они не заменяют повторную
проверку готовой поставки в Windows/Element.

## Пользователь и проект

При открытии Codex плагин обращается к Console с текущими `1C.clientId`/`1C.clientSecret`. Он получает пользователя через `/console/api/v2/me` и имя проекта через `/console/api/v2/projects/{1C.projectId}`. Эти запросы не используют proxy для OpenAI; сервер Element должен видеть собственную Console по адресу `1C.server`.

Ключ пользователя включает сервер Console, список пользователей и ID пользователя. Ключ проекта включает сервер, пространство и имя проекта. Явное `space-id: null` обозначает отдельную область проектов без пространства. Отсутствующее или пустое поле плагин не принимает. Application ID, project ID развертывания и путь workspace не входят в ключ каталога.

Для RC потребуется войти в Codex под подтвержденным пользователем IDE. Плагин не копирует токены из произвольных старых профилей. Учетная запись OpenAI и пользователь IDE имеют разные назначения: выход из OpenAI не меняет владельца чатов.

При смене workspace внутри того же подтвержденного проекта плагин сохраняет ID native-thread и возобновляет его с новым cwd. Новый путь проверяется по ответу app-server; молчаливый возврат к старому cwd запрещен. Если app-server явно подтверждает отсутствие старого диалога, остается существующий переход к новому thread с ограниченной выдержкой из истории проекта. [Контракт восстановления и экспериментального контекста](experimental-context.md).

## Проверка Console без MCP в 1.0.2-rc

Плагин использует собственный `ElementConsoleClient`. MCP не участвует в проверке владельца истории. Необязательный `ElementMcpIdeBridgeService` передает контекст IDE во внешний 1C Element MCP; его отсутствие или ошибка синхронизации не блокируют Console API, чаты и вход в Codex.

При открытии sidebar плагин читает настройки текущей IDE: `1C.server`, `1C.clientId`, `1C.clientSecret`, `1C.projectId`. Затем обращается к Console: `/sys/token`, `/api/v2/me`, `/api/v2/projects/{projectId}`. Плагин не получает чужую сессию из MCP, переменных окружения или прежнего профиля. Токен Console живет в памяти на время проверки и не попадает в историю, сообщения Codex или логи.

Клиент принимает `id_token` и `access_token`, сохраняет префикс адреса при reverse proxy и один раз обновляет токен после HTTP 401. HTTP 403 и другие ошибки не вызывают повторный вход под другим пользователем. Запрос ограничен 8 секундами и 1 MiB ответа. При смене учетных данных плагин отменяет текущую проверку; ответ прежнего пользователя не открывает историю.

Проверка полей поддерживает `user-list-id`/`userListId`, `is-active`/`isActive`, `space-id`/`spaceId`. Противоречащие значения плагин отклоняет. Ключи существующей истории не изменены. Плагин по-прежнему требует подтвержденные ID пользователя и списка пользователей, имя и пространство проекта. Для уже поддержанного явного `space-id: null` сохранена прежняя отдельная область; отсутствующее пространство не превращается в нее.

1. Остановите внешний 1C Element MCP и перезапустите IDE. Откройте Codex. Проверка Console и загрузка истории должны работать без процесса MCP.
2. В логах найдите `Element Console identity verified`. При отказе найдите `Element Console identity rejected`: строка содержит только этап, код ошибки и имена проблемных полей.
3. Например, `stage=identity; code=identity_fields; fields=project.space-id:missing` означает, что Console не передала пространство. `project.id:mismatch` означает, что ID в ответе отличается от проекта текущей IDE. `stage=user; code=http_status; http=403` означает отказ Console на `/me`.
4. Создайте диалог и откройте другое приложение того же проекта под тем же пользователем. Проверьте историю. Под другим пользователем она не должна появиться.
5. При повторении ошибки пришлите строки `Element Console identity`, версию плагина и бандла Element. Не присылайте полный ответ `/me`: он может содержать токены доступа.

### Отказ по `user.is-active` на Windows-стенде

В логе `2026-09-08T21:33:43.112Z` плагин записал `fields=user.is-active:inactive`. Console выдала токен и ответила на `/me` и запрос проекта, но наша проверка отклонила `is-active: false`.

В бандле 9.2.4-6 прослежена цепочка:

- В `com.e1c.g5rt.server.paasmanager-9.2.4-6.jar` обработчик `API_V2/MyUserHttpController.xbsl` вызывает `ApiUsersService.GetMyUser`. Тот получает текущего пользователя и сериализует его через `UserListMappers.UserDataToUser` и `UsersStructures.CreateJson`.
- В `com.e1c.g5rt.usermanager.webapp-9.2.4-1.jar` метод `UserMapper.toDto` вычисляет `is-active` сравнением статуса с `UserStatus.ACTIVE`. Перечисление `UserStatus` содержит также `NEW` и `BLOCKED`, поэтому по `false` нельзя определить запрет доступа.
- В `com.e1c.g5rt.authentication.app-9.2.4-1.jar` метод `AuthTokenService.getAuthUserToken` ищет пользователя по client ID, проверяет client secret и выпускает токен с ID пользователя и списка. Этот путь не требует `is-active=true` и не переводит пользователя в `ACTIVE`.

Плагин больше не использует этот флаг как самостоятельный запрет. Решение о доступе остается у Console: он требует успешные ответы на получение токена, `/me` и запрос текущего проекта. HTTP 401/403, неподтвержденные идентификаторы, несовпадение проекта и удаленный проект по-прежнему закрывают историю. Проверки типов и противоречащих алиасов сохранены. Ключи каталогов истории не менялись.

`npm run check:identity` воспроизводит `is-active: false` через HTTP-стенд, проверяет неизменность владельца истории, отказ на каждом из трех этапов при HTTP 401/403 и сброс ранее подтвержденной личности при ошибке повторной проверки. Сценарии смены A/B/C включают пользователя B с этим флагом. До исправления положительные регрессионные тесты воспроизводили ошибку из лога. Повторный запуск исправленной поставки на Windows-сервере остается необходимым.

## Перенос старых чатов

Старый JSON не удостоверяет владельца: одинаковый login может существовать на разных серверах и в разных списках пользователей. Администратор должен подтвердить, кому принадлежит выбранный архив. Сам RC не сканирует чужие каталоги и не выбирает профиль по имени.

1. Откройте или создайте чат после подтверждения пользователя IDE. В поиске истории откройте «Перенос истории».
2. В `<configRoot>/users/<userKey>/projects/<projectKey>/` появится `import-target.json`. В нем указаны проверенные сервер, пользователь, пространство и имя проекта. Токенов в файле нет.
3. На сервере администратор проверяет прежний `users/<старый-профиль>/workspaces/<workspace>/chats.json` и запускает экспорт из каталога нового плагина:

```text
node scripts/export-legacy-history.js --source "ПУТЬ_К_СТАРОМУ/chats.json" --binding "КАТАЛОГ_ПРОЕКТА/import-target.json" --confirm-owner "ID_ПОЛЬЗОВАТЕЛЯ" --confirm-project "ИМЯ_ПРОЕКТА"
```

Замените значения на пути сервера и точные `owner.userId` / `scope.projectName` из `import-target.json`. Вместо системного `node` можно использовать поставляемый `browser/<platform>/node/node.exe` на Windows или `browser/<platform>/node/node` на Linux. Пути с пробелами заключайте в кавычки.

4. Экспорт создаст копию в `imports/` выбранного проекта. Исходный JSON и файлы авторизации останутся на месте.
5. Обновите список переноса в чате, выберите архив и подтвердите перенос. Повторный импорт того же архива не дублирует диалоги.

RC не импортирует старые активные запросы, очередь и учетные данные. Вложения со старым абсолютным путем могут потребовать повторного прикрепления; плагин не разрешает доступ к чужому каталогу ради такого файла. Импорт добавляет диалоги, не заменяя текущие сообщения. При смене пользователя во время переноса данные остаются в области исходного владельца и не появляются у нового пользователя.

## Ошибки хранения

При поврежденном JSON RC прекращает запись и показывает путь файла. Не удаляйте его: сначала сохраните копию и проверьте `chats.json.bak`. При конфликте двух IDE текущая версия остается в `chats.json.conflict-*.json`.

Аварийное завершение IDE может оставить каталог `chats.json.lock`. RC не снимает такую блокировку автоматически, чтобы другой процесс не потерял запись. Администратор должен остановить все IDE, использующие этот проект, сохранить копию истории и только после этого удалить оставшийся каталог блокировки. Затем можно открыть IDE снова.

## Приемочные сценарии

### Ответы на вопросы

- [ ] Асинхронный вопрос с вариантами отображается кнопками в сообщении. Нажатие отправляет выбранный ответ один раз, не стирая черновик основного поля ввода.
- [ ] Для вопроса без вариантов доступны строка и «Ответить». Проверить Enter, отказ сервера и повторную отправку без потери текста.
- [ ] Прокрутить вопрос за пределы видимой истории во время поступления ответа агента, затем вернуться: черновик сохранён, отправленный ответ не запрашивается повторно.
- [ ] Проверить RPC-вопрос с несколькими полями, своим вариантом и секретным ответом. Форма находится в истории, а не в модальном окне; отмена и истечение срока закрывают запрос штатно.
- [ ] Переключить чат во время отправки. Ответ должен остаться в исходном диалоге. В архивном чате отправка недоступна.

Автоматическая проверка: `npm run check:chat-questions`. Она использует браузерный
webview и тестовый host; проверка настоящего runtime и Windows/Element проводится отдельно.

### Панель настроек

Контракт перенесённого макета, токены, поведение и команды: [Настройки Codex для 1С:Элемент](settings-ui.md). Чеклист приёмки в IDE, не отметки о выполненных автотестах:

- [ ] Проверить пять разделов, локальные иконки, светлую/тёмную тему и узкую ширину; встроенный MCP не дублируется, URL приложения IDE только для чтения.
- [ ] Проверить фокус и закрытие правой панели, черновики и отмену, ошибки возле действий; базовый контекст относится к общей поставке, не отдельному проекту.
- [ ] Изменить базовый контекст: «Перечитать» доступно и показывает inline-подтверждение. «Оставить черновик» и ошибка подтверждённого чтения сохраняют текст и `revision`; успешное «Перечитать файл» заменяет их и сбрасывает `dirty`. Повторить после сообщения о конфликте файла.
- [ ] Подтвердить external/inline fallback под CSP и отдельно выполнение на Windows-сервере пользователя. Зафиксировать результаты; локальные UI-проверки не подтверждают релиз или развёртывание.

### Визуальная совместимость с master

Визуальный эталон чата RC: `master` версии 0.1.89. React-компоненты, виртуализация, потоковые обновления, сохранение черновика и серверный протокол остаются в RC. Возвращение оформления не означает возврат к vanilla renderer.

- Компактная шапка содержит название и вид чата. Шесть новых действий находятся справа в этой же строке. Развёрнутая шапка показывает учётную запись и состояние сервера.
- Пользовательские сообщения расположены справа; ответы Codex остаются без повторяющихся строк автора и времени. Копирование доступно при наведении или фокусе.
- Модель, уровень рассуждений, скорость, доступ, план, навыки, вложения и контекст находятся внутри прежнего поля ввода. Списки раскрываются над соответствующими кнопками; Escape возвращает фокус.
- Во время запроса видна кнопка остановки. При наличии черновика появляется отправка в очередь с меню рекомендации.
- Новые панели поиска, изменений, действий, артефактов и контекста остаются справа. В узком окне сохраняется адаптивное размещение панели под историей.
- Подсказки и сообщения новых модулей переведены на русский. Идентификаторы протокола, имена моделей, пути и исходные данные внешних инструментов не переводятся.

`npm run check:chat-design` проверяет расположение, размеры, меню, фокус, очередь и рекомендации на ширинах 390, 900, 1200 и 1440 px, в светлой и тёмной темах. Скриншоты сохраняются в `CODEX_TEST_ARTIFACTS` или временный каталог. Проверка включена в CI вместе с тестами потоковой прокрутки. Предпросмотр подсветки в этом UI-стенде тестовый; настоящий highlighter проверяется отдельно через `check:browser-highlighter`.

### Функциональные сценарии

- В поле сообщения Cmd+A на macOS и Ctrl+A на Windows выделяют только его текст. Enter отправляет запрос, Shift+Enter добавляет строку; выделение вне поля остаётся штатным.
- В «Система → Управление контекстом» проверьте включение, отключение и повторное открытие после перезапуска IDE. Во время ответа переключение не должно прерывать генерацию. Требования к подписке и ограничения проверки описаны в [документации режима](experimental-context.md).
- Во время длинного ответа прокручивайте вверх, выделяйте текст и набирайте следующий запрос. Позиция, выделение и черновик должны сохраняться; кнопка перехода вниз возвращает к ответу.
- Проверьте длинную историю, границы страниц и переход из поиска к старому сообщению.
- Во время работы раскройте команду или поиск. После завершения проверьте сворачивание операций, видимый ответ и отдельный diff.
- Попросите Codex задать уточняющие вопросы. Проверьте варианты, свой ответ, отмену и переход фокуса клавишей Tab.
- Добавьте запрос в очередь. Остановите runtime до отправки: текст должен остаться доступным для повтора. Рекомендация должна попадать в текущий запрос.
- Откройте измененный файл в review. Проверьте stage и отмену выбранного изменения. При несохраненном редакторе или изменившемся файле плагин должен отказать и предложить обновить данные.
- Проверьте ссылки на файлы, Markdown-таблицы, XBSL/YAML и копирование на обычном HTTP, затем в темной теме.
- Создайте чат в одном приложении проекта, откройте другое приложение того же проекта и пользователя. История должна сохраниться; другая учетная запись IDE или другое пространство не должны ее получить.
- В двух IDE измените разные чаты одного проекта. Обе правки должны сохраниться. При одновременной правке одного чата ожидается сообщение о конфликте и отдельный файл версии, а не молчаливое затирание.
- Перезапустите IDE во время ответа. Проверьте сохраненный текст и восстановление панели без зависшего прелоадера.

## Комплектность Code Mode и MCP

В поставке Codex 0.154.0 рядом с `codex.exe` требуется `codex-code-mode-host.exe` (на Unix: `codex-code-mode-host`). Этот компонент выполняет Code Mode и вложенные вызовы инструментов, включая MCP. В первоначальном импорте 0.153.4 его пропустили; проверка сборки тоже не требовала этот файл. Это ошибка комплектации runtime, а не React или внешнего MCP.

Компонент поставляется для всех платформ из того же официального релиза 0.154.0, что и основной Codex. SHA-256 архивов проверены по GitHub release metadata, контрольные суммы распакованных файлов записаны в `bin/runtime-manifest.json`. Новые файлы учитываются Git LFS. Сборщик переносит все вспомогательные бинарники из `--runtime-root` и сохраняет их при повторном деплое из checkout с поинтерами. Проверка поставки отклоняет отсутствие файла, поинтер, неверный формат/архитектуру, права исполнения Unix и несовпадение контрольной суммы. Перед запуском плагин отдельно проверяет наличие и формат Code Mode host, не запуская его и не читая большой бинарник целиком.

`npm run check:runtime-payload` проверяет эти сценарии на временных файлах. `node scripts/code-mode-mcp-smoke.cjs bin/<platform>/codex[.exe]` запускает настоящий app-server и Code Mode host с локальными HTTP-стендами Responses и MCP. Проверяется полный путь до `tools/call` и возврат результата. Учетная запись OpenAI, пользовательская конфигурация и внешний сервер не используются. Вариант `--expect-missing-host` создает изолированную копию Codex без компонента и подтверждает отказ до обращения к MCP. Оба варианта включены в сборку Windows/Linux в CI.

После замены поставки перезапустите серверную IDE. Проверьте наличие `bin/win32-x64/codex-code-mode-host.exe` и повторите запрос через ваш MCP. Успешный локальный smoke-тест не подтверждает доступность, авторизацию или права самого удаленного MCP-сервера.

## Браузер и границы Element

Кнопка «Проверить браузер» не запускает `chrome.exe --version`: этот способ проверки непереносим на Windows. Проверяются Node.js и запуск Playwright MCP, затем Playwright открывает Chromium без окна с временным профилем, загружает автономную тестовую страницу, нажимает кнопку и читает версию через `browser.version()`. Браузер закрывается после теста. Ожидание запуска ограничено; при зависании используется существующий менеджер дочерних процессов, который завершает только принадлежащий проверке процесс и его дерево. Повторные нажатия не создают параллельные проверки. Ошибка содержит этап и попадает в логи Codex.

«Компоненты установлены» означает только наличие файлов в поставке. Успешный запуск подтверждается отдельным результатом проверки; доступность URL приложения и его авторизацию этот автономный тест не проверяет. Настройка Chromium sandbox автоматически не меняется.

`npm run check:browser-runtime` проверяет запуск без прямого вызова Chrome, ошибки, таймауты, повторные запросы и закрытие браузера. `node scripts/browser-runtime-smoke.cjs ПУТЬ_К_BROWSER_RUNTIME` проверяет кнопку настроек и реальную цепочку MCP: подключение, список инструментов, открытие локальной HTTP-страницы, снимок структуры, нажатие кнопки и закрытие. Используется текущая схема `browser_click.target` из встроенного MCP 0.0.78. Тест включен в Windows/Linux release CI после подготовки браузера. Без явных development-параметров запуск чужих платформ запрещен; локальная проверка с нативными Node.js/Chrome не выдается за проверку Windows-бинарников.

Включите браузерное тестирование для пользователя и проекта. Адрес приложения определяется автоматически из `1C.applicationId` через Console. В настройках нет ручного URL и списка origins; ошибки сохранения появляются рядом с кнопками соответствующего раздела. При недоступности Console отображается причина и кнопка повторной проверки. Старый URL из настроек не используется. Проверка Chromium доступна независимо от адреса приложения; выключить браузер можно и без Console.

Сетевого списка разрешённых адресов в конфигурации Playwright нет. Проверьте вложенную страницу приложения, загрузку ресурсов с другого адреса и переход на другой сайт, доступный с сервера. Автоматически найденный URL задаёт только стартовую страницу. Сессия получает собственный каталог артефактов; временное имя MCP не сохраняется в общей конфигурации. Автоподтверждение относится только к этому управляемому MCP и активному запросу.

`check:browser-runtime` также проверяет Console API, смену приложения, запоздалые ответы, отказ от старого URL и сообщения об ошибках. `check:settings-browser` проверяет реальный webview-скрипт на широком и узком экране, в светлой и тёмной теме. Сценарий MCP smoke включает вложенную страницу, внешний скрипт и переход на другой origin.

Действия проекта зависят от команд бандла и готовности LSP. RC позволяет посмотреть диагностики и открыть приложение, когда IDE подтверждает такую возможность. Он не создает независимый Element workspace через `git worktree` и не запускает публикацию или произвольные terminal/tasks-команды.

Проверки на машине сборки не заменяют запуск на целевом сервере. Отдельно проверьте права системного пользователя, Chromium sandbox, сетевые ограничения и остановку дочерних процессов на Windows/Linux. Не включайте `--no-sandbox` без решения администратора.
