# Контекст YAML, XBSL и документации

Первый этап объединил структурный индекс проекта, данные работающего Language
Server и синтаксическое дерево штатного парсера Element. Второй этап выбирает
окружение конкретной задачи и раскрывает связанные объявления между модулями.
Приоритет: правильное понимание проекта и качество изменений, а не минимальный
объём контекста. Собственного XBSL-парсера
нет. Без IDE и без Java сохраняется поиск по локальному индексу; недоступность
дополнительных источников не считается отсутствием символа или ошибкой проекта.

## Что происходит при запросе

1. Существующий маршрутизатор решает, нужен ли проектный контекст. Общий чат не
   получает его автоматически. Настройки документации и правил продолжают действовать.
2. Индекс v3 читает YAML структурным парсером, выделяет объявления XBSL и сохраняет
   имена, диапазоны, типы и ссылки на обработчики. Это ещё не семантический анализ.
3. Поиск выбирает релевантные фрагменты. Для двух первых YAML/XBSL-файлов собирается
   ближайшее окружение: одноимённые YAML и XBSL, включая модули `Имя.Объект.xbsl`.
   Пара YAML/XBSL считается одним стартовым элементом: при сравнении двух компонентов
   первый не занимает оба места. Ближайшее окружение дополняется зависимостями,
   всего рассматривается не более десяти файлов.
4. Для XBSL штатный парсер строит полное дерево. Из него берутся точные диапазоны
   объявлений, типы и локальные вызовы. В запрос модели идут выбранные тела методов
   и связи, а не всё дерево проекта. Для явного запроса только сигнатуры берутся
   параметры, значения по умолчанию, аннотации и возвращаемый тип без тела.
   Вопросы о поведении или исправлении сохраняют полную реализацию.
5. Через публичный API Theia запрашиваются document symbols, definition и hover
   для выбранных позиций в XBSL и YAML. Плагин использует уже работающие провайдеры;
   не запускает второй Language Server и не переключает его проект. Цель definition
   раскрывается до содержащего её объявления, а не остаётся одной строкой.
   Из выбранных методов прослеживаются зависимости глубиной до двух переходов.
   Циклы не приводят к повторному включению тел методов.
6. Типы из выбранных файлов дополняют обычный поиск документации. Для этой связи
   используются точные идентификаторы заголовков, а не совпадение подстрок:
   `ФормаОбъекта` не подменяет `Форма`. Документация не загружается, если она отключена
   маршрутизатором или пользователь явно выбрал другой набор документов.
7. Полученные блоки проходят общий бюджет контекста. Правила проекта
   остаются отдельным источником требований: AST не доказывает их соблюдение и не
   заменяет их. Общий бюджет увеличен с 60 до 128 тысяч символов; для проектных
   маршрутов базовые и пользовательские правила получают место раньше дополнительных
   материалов. Собственные лимиты этих правил не менялись.

## Подбор под задачу

- В первую очередь включаются полные явно запрошенные методы. Большой YAML или
  вспомогательный метод не должен вытеснять основной код задачи.
- В YAML выбираются упомянутые обработчики и соседние свойства того же элемента,
  например доступность и событие кнопки. Совпадение имени всей формы не требует
  автоматически включать все её обработчики.
- Если LSP не разрешил вызов, неполное окружение не объявляется полным. Для простого
  обращения `ОбщийМодуль.Метод()` допускается кандидат по YAML-описанию общего модуля
  в том же проекте. Переменная или параметр с таким именем запрещают эту догадку.
  Область видимости, перегрузки и динамическая диспетчеризация ею не доказываются.
- Импорты выбранного модуля сохраняются как контекст пространств имён. Точные
  диапазоны перекрывающихся фрагментов объединяются; одинаковый текст из разных
  файлов не считается дубликатом.
- Неизвестный идентификатор не должен незаметно превращать поиск в обзор проекта.
  Отсутствие результатов означает отсутствие совпадений в доступном индексе,
  а не доказательство отсутствия символа у компилятора.
- Лимит служебного `project.search` увеличен до 36 тысяч символов. При упаковке
  ответа целый метод либо помещается, либо пропускается с явным уведомлением.
  Обрезанные ещё на этапе чтения большие фрагменты отдельно помечаются неполными.

## Что означает связь

| Метка | Основание | Чего она не доказывает |
| --- | --- | --- |
| `lsp` | Провайдер IDE вернул definition | Что весь проект корректен и сервер закончил переиндексацию |
| `structural` | YAML-ссылка совпала с объявлением метода в парном модуле | Что компилятор разрешил именно этот обработчик |
| `candidate` | Совпали имя типа либо имя локального вызова и объявление | Разрешение перегрузок, наследования, видимости и динамических вызовов |
| `ambiguous` | Подошли несколько объявлений | Какое из них нужно выбрать |
| `unresolved` | В выбранном окружении не найдено подходящего объявления | Что объявление отсутствует во всём проекте |

Публичные команды VS Code API агрегируют провайдеры и не сообщают, какое расширение
вернуло каждый результат. Перед обращением проверяются активность штатного расширения
Element и регистрация его bridge-команды, но это не подтверждение готовности LSP.
Пустой ответ не превращается в утверждение «символа нет».

## Штатное дерево

Собственный небольшой Java-helper вызывает `BslParserHelper.parse` из установленного
Element и выгружает всё дерево EMF containment: узлы, роли детей, примитивные атрибуты,
диапазоны UTF-16 и синтаксические диагностики. Семантические cross-reference не
обходятся. Неподдержанные типы атрибутов отмечаются; исходный текст доступен по диапазону.
Частичное дерево при синтаксической ошибке не объявляется полным.

JAR Element в поставку плагина не включается. Адаптер ищет его через
`LSP_SERVER_PATH`, каталог штатного расширения и соседний `@1c-appengine-plugin`.
Java выбирается через `E1C_IDE_JAVA_HOME`, `JAVA_HOME`, затем `PATH`. Нужен Java 11
или новее; совместимость конкретного штатного JAR с Java определяется самим Element.
Helper собирается в Java 11 bytecode. Для запуска готового плагина JDK не нужен.

Java-процесс запускается лениво и переиспользуется, останавливается при простое и
при выгрузке расширения. Кеш AST учитывает содержимое файла и версию парсера/helper.
Ограничены очередь, размер входа/выхода и кеш. Для дополнительного анализа AST/LSP
и чтения выбранных файлов действует общий бюджет ожидания 8 секунд. Финальная
проверка актуальности имеет отдельное общее окно до 1 секунды; непроверенные фрагменты
исключаются. Первичное построение локального индекса в эти бюджеты не входит.

## Изменения и границы

- Индекс хранится в `project-index-v3.json`. Старый v2 не удаляется и не используется
  как новый формат. Одинаковые файлы в разных каталогах имеют разные ID фрагментов.
- Несохранённый текст редактора подставляется только в текущий запрос и не попадает
  в дисковый индекс. Перед возвратом проверяются снимки; устаревшие данные исключаются.
- Корень workspace фиксируется на запрос. Смена workspace не должна смешивать
  фрагменты двух проектов. YAML-связи типов ограничены ближайшим `project.yaml`.
- В подбор попадает до 20 семантических фрагментов с общим бюджетом 32 тысячи
  символов и лимитом 24 тысячи на один фрагмент. Форматирование и метаданные также
  должны поместиться в итоговые 36 тысяч символов `project.search`.
  Большие методы помечаются как неполные. Весь индекс по-прежнему ограничен
  существующими лимитами файлов и размера; это не глобальная база всех зависимостей.
- Документация сопоставляется по именам, а не по стабильным идентификаторам компилятора.
  Версии сравниваются только по явным метаданным официального источника и установленного
  штатного парсера. Совпадение версии расширения IDE не используется вместо версии языка.
  Неизвестная версия и несовпадение явно отмечаются; полезный документ не исчезает
  только из-за отсутствия метки. Совпадение меток не доказывает совместимость всех API.
- Нового MCP-сервера для этой функции не требуется.

## Кеш и актуальность

У разных данных разные сроки жизни:

- Дисковый индекс переиспользуется между запросами. Изменения файлов помечают его
  устаревшим; обновление выполняется при следующем обращении. Правки в открытом
  редакторе накладываются поверх индекса, но не записываются в него.
- Штатный AST кешируется по содержимому и версии парсера/helper. Новый текст не
  может получить дерево предыдущей редакции.
- Готовое окружение конкретного запроса имеет небольшой кеш: до восьми записей,
  до 2 МиБ, не дольше пяти секунд от начала анализа. Ключ учитывает точный запрос,
  профиль, корень и ревизию workspace, хеши индекса, открытые буферы и параметры
  поиска. Короткий срок нужен потому, что готовность и результаты LSP могут
  меняться без изменения исходников. Попадание в кеш не продлевает этот срок.
- На попадании повторно проверяются хеши и допустимость путей только использованных
  файлов и зависимостей, не весь проект. Правки, открытие/закрытие буфера, события
  файловой системы, смена workspace и выгрузка сервиса сбрасывают кеш. Сбой проверки
  не разрешает возвращать прежний результат.
- Ошибки, недоступный или частичный AST/LSP, обрезанные фрагменты, пропущенные
  участки и пустые результаты не кешируются как законченный анализ. Без готового
  LSP всё ещё переиспользуются индекс и AST, но готовность LSP проверяется заново.

Это кеш данных для подбора, а не сохранённый запрос модели. Правила проекта
подключаются отдельно при каждом запросе: изменение `.local-codex/rules.md`
не требует перестроения AST и не скрывается за кешем семантического окружения.
Сам файл правил небольшой и по-прежнему перечитывается; отдельный кеш для него
на этом этапе не добавлен.

## Проверка второго этапа

Сравнение на восьми задачах реального проекта, эталонные диапазоны, размеры
фактически возвращённых блоков и ограничения измерения:
[отчёт второго этапа](project-context-stage2-evaluation.md).
Увеличение выходного лимита измеряется отдельно от сравнения при одинаковом лимите.
Проверки с имитацией LSP покрывают раскрытие определений, неоднозначность, два
перехода между объявлениями, циклы, изменения документов и неполные ответы.
Они не заменяют сквозную проверку провайдеров в живой IDE.

## Проверка первого этапа

Тестовый проект: `https://gitflic.ru/project/a-volkov/privet-dom-app`, commit
`5f3e72ed3afed7d04b9af8b700fe5094c847ee32`. Парсер из бандла `9.1.9-17`,
JAR `9.1.9-1`; локальная Java Temurin 21.0.8. Проект не изменялся.

Полный прогон: 258 XBSL-файлов, 60 236 узлов 67 видов, 1064 метода. Все файлы
разобраны без синтаксических диагностик и частичных деревьев. Нарушений границ
узлов не найдено. Лексический индекс нашёл 1063 метода; штатное дерево нашло также
объявление с аннотацией на той же строке. Это проверка синтаксиса и выгрузки дерева,
а не корректности проекта с точки зрения компилятора.

Дополнительная проверка сборщика символов: извлекаются все 2909 вызовов из дерева,
включая 2291 динамический. Получение имени динамического вызова не означает,
что определён его целевой метод. Литералы длительности сохраняют исходную запись
и тип штатного значения, чтобы `1ч` не превращался в безымянное число.

Контрольные задачи в `ЗамещениеПользователяФорма`:

| Задача | Что должно попасть в контекст |
| --- | --- |
| Какая проверка выполняется при нажатии «Применить»? | YAML-событие, `Применить`, тело вызываемого `МожноПрименить` |
| Почему нельзя сохранить неправильный период? | YAML-условие доступности и полный `МожноПрименить` |
| Почему нельзя назначить себя замещающим? | YAML-ссылка на подсказку и полный `ПодсказкаПроверки` |

Проверенные по исходникам факты для будущего сравнения ответов:

- `Применить` сначала вызывает `МожноПрименить` и выходит при отрицательном результате.
  YAML использует ту же проверку в свойстве `Доступность` кнопки.
- При добавлении обе даты обязательны; дата окончания должна быть строго позже
  даты начала. В режиме удаления другая ветка: проверяются замещающий и идентификатор
  замещения, а не период.
- Выбор текущего пользователя запрещён в `МожноПрименить`; `ПодсказкаПроверки` выдаёт
  отдельное объяснение для этого случая. Текст подсказки и ограничение кнопки связаны,
  но это два разных метода.

В этих трёх задачах новый подбор возвращает все четыре ожидаемых тела методов
и соответствующие YAML-связи. Старые поисковые превью не содержали ни одного тела
целиком. Сравнение не уравнивает объём текста: новый контекст больше, около 13 тысяч
символов против 2,5–3,4 тысячи превью. Поэтому это не доказательство экономии токенов
и не оценка качества ответов модели. Задачи близкие и относятся к одной форме.

Воспроизводимый запуск (пути заменить на свои):

```sh
npm run check
CODEX_NATIVE_AST_TEST_JAR=/path/to/appengine-lsp.jar node --test tests/native-xbsl-ast.test.cjs tests/project-structure.test.cjs
node scripts/evaluate-project-context.cjs --project /path/to/privet-dom-app --parser-jar /path/to/appengine-lsp.jar --baseline-ref <commit-before-change> --scan-all --output /tmp/context-evaluation.json
```

Скрипт возвращает ненулевой код, если потеряны ожидаемые методы или YAML-связи.
Сохранённый результат: [project-context-evaluation.json](project-context-evaluation.json).
Замеры задержки в отчёте выполняются с предварительно запущенным парсером и не
характеризуют холодный запуск на Windows Server.

## Что проверить в живой IDE

Работающая тестовая IDE на момент реализации недоступна. Пока не проверены фактические
ответы её Language Server и поведение новой интеграции на Windows Server.

1. Открыть этот проект в Element, дождаться его штатной индексации, включить проектный
   контекст и задать три контрольных вопроса выше. Проверить пути и диапазоны источников.
2. Сравнить definition/hover, полученные плагином, с переходом к определению и подсказкой
   самого редактора в YAML и XBSL. Пустые ответы должны давать частичный контекст, не ошибку.
3. Изменить тело метода без сохранения. Запрос должен использовать буфер, а дисковый
   индекс не должен содержать правку. Повторить с CRLF-файлом.
4. Переименовать обработчик, поменять тип в YAML, удалить файл. Проверить, что старые
   связи не выдаются как актуальные. Переключить workspace во время запроса.
5. При недоступном Java/штатном JAR проверить обычный поиск и отсутствие зависания.
6. Для оценки ответов модели выполнить одинаковые задачи на старой и новой сборке
   с одной моделью и настройками. Сравнить правильность объяснения, число ручных чтений,
   объём контекста и время ответа. Эта оценка пока не проведена.
